Time Series Features — Use Case Mapping

MongoDB Time Series collections provide purpose-built optimizations for VTMS telemetry. Below are the specific features and how each directly addresses a KSRTC use case.

Core Time Series Capabilities

🗂️ Automatic Data Bucketing

Use Case: Ingest 70M GPS pings/day without performance degradation

MongoDB groups GPS pings from the same vehicle into internal "buckets" covering minutes of data per bucket. Metadata (vehicleId) stored once per bucket, not per document.

  • 10x storage reduction — 14 GB/day raw → ~1.4 GB compressed
  • Faster range queries — scanning buckets, not individual docs
  • Zero application-level logic needed — fully automatic

⏰ TTL Auto-Expiry

Use Case: Retain GPS data for exactly 90 days, no manual cleanup

expireAfterSeconds: 7776000 — MongoDB automatically deletes data older than 90 days. No cron jobs, no partition management, no storage runaway.

  • Storage stays constant at ~150 GB (90-day window)
  • Compliance-friendly — guaranteed expiry
  • Zero operational overhead

📊 Columnar Compression

Use Case: Minimize storage cost for massive telemetry data

Time Series collections use columnar compression (zstd) within each bucket — similar values across GPS readings (same coordinates area, similar speeds) compress extremely well.

  • ~90% compression ratio on GPS data
  • Lower IOPS for range scans (less data to read)
  • No decompression overhead for queries (read-optimized)

🔍 Secondary Indexes on Time Series

Use Case: Query historical GPS by location (geofence history)

Time Series collections support secondary indexes including 2dsphere. This enables queries like "all buses that passed through zone X between 2-4 PM".

  • 2dsphere index on location field
  • Compound index on time + location
  • Speeds up historical geospatial queries from seconds to ms

Window Functions ($setWindowFields) — Feature-by-Feature

Window functions run computations across ordered sequences of GPS documents inside the database, eliminating the need to transfer millions of records to the application layer.

🚨 Harsh Braking / Acceleration Detection

RFP Requirement: Detect unsafe driving behavior in real-time

Compares speed at time T with T-10s using $shift. Calculates acceleration: (speed₂ - speed₁) / Δt. Threshold: ±4 m/s².

Operator: $shift(output: '$speed', by: -1) + $dateDiff

🛑 Unauthorized Stop Detection

RFP Requirement: Detect stops >3 min outside scheduled locations

Counts consecutive pings where speed ≤ 2 km/h using a sliding window of 18 readings (3 minutes at 10s intervals). If all 18 are stationary → unauthorized stop.

Operator: $sum with window [-17, 0] (documents range)

📡 Signal Gap / Loss Detection

RFP Requirement: Track GPS device connectivity, show gaps in playback

Computes seconds between consecutive pings. If gap > 30s → signal lost marker. Used in route playback to show dashed lines where GPS signal was lost.

Operator: $shift(output: '$timestamp', by: -1) + $dateDiff(unit: 'second')

⚡ Sustained Overspeed

RFP Requirement: Distinguish real overspeed from GPS jitter

Averages speed over 30-second window. Only triggers if average exceeds limit — eliminates false positives from single erroneous GPS readings.

Operator: $avg with time range window [-30, 0] seconds

📍 ETA Prediction

RFP Requirement: Dynamic ETA recalculated per GPS ping

Exponential moving average weights recent speeds higher than older ones, providing a smoothed velocity that accounts for current traffic conditions.

Operator: $expMovingAvg(N: 10)

🔧 Breakdown Inference

RFP Requirement: Auto-detect breakdowns from telemetry patterns

If average AND max speed = 0 for 5+ minutes after prior movement → breakdown candidate. Combined with ignition=ON to distinguish from scheduled stops.

Operator: $avg + $max with 5-minute range window

🗺️ Route Playback with Context

RFP Requirement: 90-day route replay with speed/gap visualization

Simple time-range query returns all GPS breadcrumbs. Window functions enrich each point with gap detection and speed delta — frontend animates with color-coded trail.

Query: { vehicleId, timestamp: { $gte, $lte } } + $setWindowFields

🚏 Stop Skipping Detection

RFP Requirement: Detect when bus skips a scheduled stop

Compares sequence of stops visited (detected via proximity check) against scheduled stop sequence. Missing entries = skipped stops.

Operator: $setWindowFields for sequence ordering + application-layer comparison

MongoDB Atlas Platform Capabilities

Beyond Time Series, MongoDB Atlas provides enterprise platform features that address KSRTC's requirements for availability, scaling, disaster recovery, and operational simplicity.

Auto-Scaling

📈 Compute Auto-Scaling

Use Case: Handle peak-hour GPS spikes (morning/evening rush) without over-provisioning
  • Automatically scales cluster tier up/down based on CPU, memory, IOPS thresholds
  • Configurable min/max tier bounds (e.g., M50–M80 range)
  • Scales within minutes — no downtime, no manual intervention
  • Handles 2x peak traffic (morning departure wave: ~12,000 writes/sec vs avg 8,000)

💾 Storage Auto-Scaling

Use Case: Storage grows with data without pre-provisioning disks
  • Atlas automatically extends storage when usage exceeds threshold
  • Combined with TTL — storage remains bounded after initial 90-day fill
  • No DBA intervention needed

Disaster Recovery & Business Continuity (DR/BCP)

🛡️ High Availability & DR Architecture

RFP Requirement: 99% availability, zero SPOF, disaster recovery

Within Region (HA)

  • 3-node replica set across 2 Availability Zones
  • Automatic failover in 10-30 seconds
  • Atlas SLA: 99.995% uptime guarantee
  • Self-healing — failed nodes auto-replaced
  • Rolling upgrades — zero downtime patches

Cross-Region (DR)

  • Read-only replica in DR region (e.g., Hyderabad)
  • Asynchronous replication (typical lag < 1s)
  • Can promote to primary in disaster scenario
  • Continuous backup with cross-region snapshots
  • Point-in-time restore: 1-second granularity

🔄 Backup & Restore

Use Case: Accidental data deletion, corruption recovery, compliance
  • Continuous backup — every oplog entry captured
  • Point-in-time restore to any second within retention window
  • Retention: 7 days continuous + monthly snapshots for 1 year
  • Cross-region snapshot copies for DR
  • Restore to new cluster for testing/validation

Sharding (Horizontal Scaling)

📐 Sharded Cluster for 2x+ Growth

RFP Requirement: System must scale to 2x the initial fleet size
  • Shard key: { "metadata.vehicleId": "hashed", "timestamp": 1 }
  • Distributes write load evenly across shards
  • Time-range queries target specific chunks (range component)
  • Atlas auto-balances data across shards
  • Enable at 1 TB storage or 15K writes/sec threshold

Current capacity without sharding: Single replica set handles ~8,000 writes/sec comfortably. Sharding needed only at 2x fleet (16,000+ buses).

Analytics Nodes

📊 Workload Isolation

Use Case: Heavy reporting queries must not impact live dashboard/tracking
  • Dedicated read-only nodes for reporting workloads
  • Custom read preference routes report queries to analytics nodes
  • Live tracking (Primary) remains unaffected by heavy aggregations
  • Can be different tier than primary (cost optimization)

Geospatial Capabilities

MongoDB provides native geospatial support with 2dsphere indexes — no external GIS database or library needed for most operations. The VTMS uses a hybrid approach: MongoDB for persistent queries and in-memory turf.js for high-throughput hot-path checks.

Implementation by Use Case

📍 Point-in-Polygon (Geofence Check)

Requirement: 800 checks/second as buses enter/exit zones

Approach: In-memory using turf.js (geofences cached at startup). Each GPS ping is checked against all relevant polygons in < 0.1ms.

Why not MongoDB: At 800/sec, network round-trip to DB would add latency. In-memory PIP is 100x faster for the hot path.

MongoDB role: Stores geofence definitions. Loaded into app memory on startup + refreshed on change.

🛤️ Route Corridor Deviation

Requirement: Detect when bus deviates from assigned route

Approach: turf.nearestPointOnLine(routeGeometry, busPosition) — calculates perpendicular distance from bus to route LineString.

Threshold: > 200m from nearest point on route = deviation alert.

MongoDB role: Stores route geometries as GeoJSON LineString. $geoNear for ad-hoc corridor queries.

🚏 Stop Arrival / Departure / Skip

Requirement: Detect when bus arrives, departs, or skips stops

Approach: Proximity check — if bus is within 50m of a scheduled stop for 10+ seconds = arrival. Sequence-aware: compares visited stops against schedule.

MongoDB role: $nearSphere for nearest stop lookup. Schedule comparison via $lookup in aggregation.

📱 Nearest Bus Stop (Passenger App)

Requirement: Show closest stops to passenger's GPS location

Approach: Pure MongoDB query using $nearSphere with 2dsphere index on bus_stops collection.

Performance: < 3ms response, results sorted by distance automatically.

Query: db.bus_stops.find({ location: { $nearSphere: { $geometry: point, $maxDistance: radius } } })

🚍 Vehicles in Zone (Real-Time)

Requirement: Show all buses currently inside a specific geofence

Approach: Query vehicle_current_state (8K docs max) with PIP check against geofence polygon. Uses in-memory turf.js for speed.

Alternative: $geoWithin on vehicle_current_state.location — < 5ms for 8K docs with 2dsphere index.

📜 Historical Zone Query

Requirement: Which buses passed through zone X between 2-4 PM yesterday?

Approach: Query gps_events (Time Series) with compound filter: time range + $geoWithin polygon.

Performance: ~50ms with compound index (timestamp + 2dsphere).

ETA/ETD Logic — PoC vs Production

POC (Current Demo): GPS ping → Change Stream → snap point to route line → compute distance to downstream stops → ETA = now + (remainingKm / effectiveSpeedKmh) + dwell padding → ETD = ETA + dwell → upsert trip_eta_predictions Production (Recommended): Kafka topic (key=vehicleId) → Stateful Worker/Flink • map-match to route segment index • speed smoothing + traffic multiplier + stop dwell model • cascade ETA across all downstream stops • confidence score + delay classification • publish only meaningful deltas (for example > 30s shift) • persist latest to MongoDB + push to dashboard/notifications Result: PoC gives deterministic near-real-time ETA for demo and customer walkthrough. Production adds traffic realism, better stability, confidence bands, and scale resilience.

Exact MongoDB Queries Used (PoC ETA)

// 1) Change Stream source (real-time trigger) db.vehicle_current_state.watch( [{ $match: { operationType: { $in: ["insert", "update", "replace"] } } }], { fullDocument: "updateLookup" } ) // 2) Upsert latest ETA/ETD vector per bus db.trip_eta_predictions.updateOne( { vehicleId: "KA-01-F-1001" }, { $set: { routeId: "RT001", currentSpeed: 31.4, currentDistanceAlongKm: 9.92, predictions: [ { stopId: "S007", stopName: "Bommanahalli", sequence: 7, remainingKm: 1.56, eta: ISODate("..."), etd: ISODate("...") }, { stopId: "S008", stopName: "Electronic City Phase 1", sequence: 8, remainingKm: 8.74, eta: ISODate("..."), etd: ISODate("...") } ], updatedAt: new Date(), source: "change_stream_worker" } }, { upsert: true } ) // 3) Dashboard/API read db.trip_eta_predictions.findOne({ vehicleId: "KA-01-F-1001" })

Stop Arrival/Departure/Skip (Sequence-aware) — Query Logic

// 1) Route sequence source (ordered stopIds) const route = db.routes.findOne({ routeId: "RT001" }) // 2) Stop metadata lookup for names/points const stops = db.bus_stops.find({ stopId: { $in: route.stopIds } }).toArray() // 3) Current sequence context from latest ETA snapshot const seqState = db.trip_eta_predictions.findOne({ vehicleId: "KA-01-F-1001" }) // seqState.nextStopSequence = expected next stop // 4) Skip evidence from alert stream const skipAlerts = db.alerts.find({ vehicleId: "KA-01-F-1001", type: "stop_skipped" }).sort({ timestamp: -1 }).limit(20).toArray() // 5) UI/API composes sequence status: // seq < nextStopSequence => completed // seq == nextStopSequence => next expected // stopId in skip alerts => skipped // else => pending // Implemented endpoint: // GET /api/dashboard/trip-progress/:vehicleId
Production Scaling Note: For 2x fleet size, we recommend adding a Kafka layer between ingestion and processing. The ingestion service writes to MongoDB AND publishes to Kafka simultaneously, giving sub-10ms processing latency and enabling multiple independent consumers.

Auditing & Compliance

VTMS handles sensitive operational data and government fleet management. MongoDB Atlas provides multiple layers of auditing and compliance controls.

Application-Level Audit Trail

📋 audit_logs Collection

Purpose: Track every operational action — who did what, when, from where
  • Every alert acknowledgment/closure logged with userId, timestamp, IP
  • Schedule changes, route modifications, vehicle reassignments tracked
  • Geofence configuration changes captured
  • TTL index: auto-expires after 1 year (31,536,000 seconds)
