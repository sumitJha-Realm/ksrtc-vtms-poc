Kafka Apache Kafka — Ingest Buffer & Decoupling

Decouple GPS device ingestion from database writes for reliability at scale

Current (PoC)
GPS Device → HTTP POST → Express → MongoDB
             (direct write, no buffer)
             
Risk: If MongoDB is slow/down,
GPS data is LOST
→
With Kafka
GPS Device → Kafka Topic → Consumer → MongoDB
             (buffered, partitioned, durable)
             
Benefit: Zero data loss,
replay capability, back-pressure
  • Throughput: Handle 80,000+ GPS messages/second (8,000 buses × 10s = 800 msg/s normal, burst to 80K during peak)
  • Durability: GPS data persists in Kafka for 7 days — even if MongoDB is down, no data loss
  • Decoupling: Multiple consumers can read same stream — one writes to MongoDB, another does real-time analytics
  • Back-pressure: If database is slow, Kafka buffers automatically — no dropped messages
  • Replay: Reprocess historical data when adding new alert rules or fixing bugs

Triggers MongoDB Atlas Triggers — Serverless Event Processing

Replace application-level Change Streams with managed, auto-scaling serverless functions

Current (PoC)
Node.js server.js
  └── changeStream.watch()
      └── Process in-memory
      
Risk: If server crashes,
alert processing STOPS
→
With Atlas Triggers
Atlas Trigger (managed)
  └── Function executes on each change
      └── Guaranteed delivery, auto-retry
      
Benefit: Survives app restarts,
auto-scales, no infra to manage
  • Resilience: Triggers run in Atlas — independent of your app server. App crashes don't stop alert processing
  • Auto-scaling: Atlas scales trigger execution based on event volume — no manual tuning
  • Guaranteed delivery: Built-in retry logic ensures no events are missed
  • Use cases: Send SMS/push notification on critical alerts, auto-escalate unacknowledged alerts, update dashboards, log audit trails
  • Integration: Call external APIs (SMS gateway, email, ticketing systems) directly from trigger functions
// Atlas Trigger Function — Overspeed Alert Notification
exports = async function(changeEvent) {
  const alert = changeEvent.fullDocument;
  
  if (alert.type === 'overspeed' && alert.severity === 'critical') {
    // Auto-escalate: notify depot manager
    await context.services.get("http").post({
      url: "https://sms-gateway.ksrtc.in/send",
      body: { phone: depotManager.phone,
              message: `CRITICAL: ${alert.vehicleId} at ${alert.details.speed} km/h` }
    });
    
    // Update alert with notification status
    await collection.updateOne(
      { _id: alert._id },
      { $set: { notified: true, notifiedAt: new Date() } }
    );
  }
};

Stream Processing Atlas Stream Processing — Real-Time Analytics

Process, aggregate, and transform streaming GPS data using MongoDB's native stream processor with MQL syntax

Current (PoC)
Post-hoc: Run $setWindowFields
on stored data (after the fact)

Limitation: Not truly real-time,
queries scan large datasets
→
With Stream Processing
Pre-compute: Process GPS stream
BEFORE it hits the database

Benefit: Results available instantly,
no heavy post-hoc queries needed
  • Tumbling Windows: Compute avg speed, distance every 1 minute per vehicle — results written to pre-aggregated collection
  • Sliding Windows: Detect harsh braking in real-time (speed delta over 10s window) — emit alert immediately
  • Native MQL: Uses same MongoDB query language — no Spark/Flink expertise needed
  • Kafka Source/Sink: Read from Kafka topics, write to MongoDB collections or other Kafka topics
  • Geofence Processing: Continuous geofence checks on the stream — no need to query after storage
// Atlas Stream Processor — Real-time Speed Violation Detection
{
  $source: { connectionName: "kafka-gps-ingest", topic: "gps-events" }
},
{
  $tumblingWindow: {
    interval: { size: 10, unit: "second" },
    pipeline: [
      { $group: {
          _id: "$vehicleId",
          avgSpeed: { $avg: "$speed" },
          maxSpeed: { $max: "$speed" },
          location: { $last: "$location" }
      }},
      { $match: { maxSpeed: { $gt: 60 } } }  // Speed limit check
    ]
  }
},
{
  $merge: { into: { connectionName: "atlas-cluster", db: "ksrtc_vtms", coll: "speed_alerts" } }
}

// Sliding Window — Harsh Braking Detection
{
  $source: { connectionName: "kafka-gps-ingest", topic: "gps-events" }
},
{
  $slidingWindow: {
    interval: { size: 10, unit: "second" },
    pipeline: [
      { $setWindowFields: {
          sortBy: { timestamp: 1 },
          output: { prevSpeed: { $shift: { output: "$speed", by: -1 } } }
      }},
      { $addFields: { deceleration: { $subtract: ["$speed", "$prevSpeed"] } } },
      { $match: { deceleration: { $lt: -20 } } }  // >20 km/h drop in 10s
    ]
  }
},
{
  $emit: { connectionName: "atlas-cluster", db: "ksrtc_vtms", coll: "alerts" }
}

Archive Online Archive — Automated Data Tiering

Automatically move old GPS data to low-cost storage while keeping it queryable

Current (PoC)
ALL GPS data in hot storage (M30+)
• 429K events = ~100MB (2 days)
• 1 year = ~18GB
• 5 years = ~90GB

Cost: All on expensive SSD,
queries slow as data grows
→
With Online Archive
Hot: Last 90 days (SSD) → fast queries
Archive: >90 days (object storage) → cheap

• Auto-tiered by archival rule
• Still queryable via same connection
• 80%+ cost reduction on old data
  • Cost Reduction: Archive storage costs ~$0.02/GB/month vs $2.30/GB for hot SSD — 99% cheaper for historical data
  • Automatic: Set a rule (e.g., "archive GPS events older than 90 days") — Atlas handles the rest
  • Still Queryable: Archived data remains queryable through the same connection string — transparent to the app
  • Compliance: Keep 5+ years of GPS history for regulatory compliance without breaking the budget
  • Performance: Hot cluster stays lean — queries on recent data remain fast
// Online Archive Rule Configuration
{
  "dbName": "ksrtc_vtms",
  "collName": "gps_events",
  "criteria": {
    "type": "DATE",
    "dateField": "timestamp",
    "dateFormat": "ISODATE",
    "expireAfterDays": 90    // Archive after 90 days
  },
  "partitionFields": [
    { "fieldName": "metadata.vehicleId", "order": 0 },
    { "fieldName": "timestamp", "order": 1 }
  ]
}

// Querying archived data (transparent to app):
db.gps_events.find({
  "metadata.vehicleId": "KA-19-F-1001",
  timestamp: { $gte: ISODate("2025-01-01"), $lt: ISODate("2025-06-01") }
})
// ↑ This query automatically spans both hot + archive tiers

Federation Atlas Data Federation — Unified Cross-Source Queries

Query across Atlas clusters, Online Archive, S3 buckets, and HTTP sources with a single MQL query

Current (PoC)
Reports query ONLY current cluster
• Can't access archived data
• Can't join with external systems
• Yearly reports impossible without
  keeping ALL data in hot storage
→
With Data Federation
Single query spans:
• Hot cluster (recent 90 days)
• Online Archive (90d – 5 years)
• S3 bucket (external CSV/Parquet)
• HTTP endpoints (weather API, etc.)

→ Unified yearly/multi-year reports
  • Unified Reports: Generate yearly fleet performance reports querying across hot + archived GPS data seamlessly
  • External Data Join: Enrich GPS data with weather (S3/HTTP), road condition data, or fuel station locations
  • No ETL Needed: Query data where it lives — no need to copy/move data into a data warehouse
  • SQL Interface: Expose federated data via Atlas SQL Interface for BI tools (Tableau, Power BI)
  • Cost-Effective Analytics: Run heavy analytical queries against federated endpoint — doesn't impact production cluster
// Data Federation — Yearly Fleet Performance Report
// Single query spans hot cluster + Online Archive + S3

// Federated Database Configuration:
{
  "stores": [
    { "name": "atlas-hot", "provider": "atlas", "clusterName": "KSRTC-Prod" },
    { "name": "atlas-archive", "provider": "atlas", "clusterName": "KSRTC-Prod",
      "readPreference": { "mode": "secondary" } },
    { "name": "s3-weather", "provider": "s3", "bucket": "ksrtc-weather-data",
      "region": "ap-south-1" }
  ],
  "databases": [{
    "name": "federated_vtms",
    "collections": [{
      "name": "all_gps_events",
      "dataSources": [
        { "store": "atlas-hot", "database": "ksrtc_vtms", "collection": "gps_events" },
        { "store": "atlas-archive", "database": "ksrtc_vtms", "collection": "gps_events" }
      ]
    }]
  }]
}

// Query (runs across all tiers automatically):
db.all_gps_events.aggregate([
  { $match: { "metadata.vehicleId": "KA-19-F-1001",
              timestamp: { $gte: ISODate("2025-01-01"), $lt: ISODate("2026-01-01") } } },
  { $group: { _id: { $month: "$timestamp" },
              totalKm: { $sum: "$distanceDelta" },
              avgSpeed: { $avg: "$speed" },
              maxSpeed: { $max: "$speed" } } },
  { $sort: { "_id": 1 } }
])
// → Monthly performance for full year, querying hot + archive seamlessly
